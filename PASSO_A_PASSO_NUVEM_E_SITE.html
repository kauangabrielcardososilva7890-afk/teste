Parte 1 — Worker publicando sozinho pela branch da sessão

A publicação automática do Worker costuma ficar apontada para uma branch antiga (arena/01a00cfb-teste, configuração de uma sessão anterior). O repositório hoje está em API 0.4.9 / Worker 5.26.8. O ajuste abaixo faz o push desta branch publicar sozinho. Não consigo verificar daqui o que está no ar — quem diz é o /health (passo "Conferir", logo abaixo).

  1. Abra https://dash.cloudflare.com e entre na sua conta.
  2. No menu da esquerda, clique em Workers & Pages.
  3. Clique no worker digicopy-sync-api.
  4. Abra Settings → procure a seção Builds & Deployments (em algumas telas aparece como Build configuration / Branch control).
  5. Confira estes três campos (é o que o README do projeto manda):
    • Root directory (pasta raiz): cloudflare-worker
    • Build command (comando de build): vazio
    • Deploy command (comando de publicação): npm run deploy
  6. Em Branch control, troque a Production branch (branch de produção) para:
    arena/01a0cf4a-teste  → clique em Save.
  7. Vá na aba Deployments e clique em Retry deployment (ou aguarde: o push que já foi feito nesta branch dispara uma build nova em segundos).
  8. Conferir: abra no navegador
    https://digicopy-sync-api.digicopyonline.workers.dev/health
    Tem que aparecer "versao":"5.26.8" (e API 0.4.9). Se aparecer 5.26.3, a build ainda não publicou — espere 1 minuto e dê Ctrl+F5.
Aviso honesto (importante): essa nuvem é a mesma que os PCs da loja usam todo dia — 15 arquivos do sistema apontam para esse endereço. Com a branch da sessão como produção, todo push nesta branch publica o worker no ar. Enquanto for assim, eu só empurro commit com o worker testado (node --check, test-pure.mjs, test-integration.sh). O deploy não apaga dados: as migrações só criam tabela/coluna; mesmo assim, o combinado é não mexer em regra do worker sem você saber.
Jeito mais seguro (se você preferir depois): manter a Production branch do worker em main e ligar “Non-production branch deploys” = Preview URLs — assim o push desta sessão gera só um endereço de preview (teste) e a nuvem que a loja usa só muda quando você publicar de propósito. Me avise se quiser esse formato.

Deu erro no build do Worker?

Erro: Failed: The build token selected for this build has been deleted or rolled and cannot be used for this build. Please update your build token in the Worker Builds settings and retry the build.

Isso não é erro do código — é o token de build guardado no painel, que ficou velho (foi editado, apagado ou “rollado” em My Profile → API Tokens). É um caso conhecido e documentado pela Cloudflare (Troubleshooting builds → Stale API token). A cura:
  1. No projeto do worker: Settings → Build → Build Configuration.
  2. No campo API token, clique em Create new token (a Cloudflare cria o token com as permissões certas — nada de colar valor no repositório).
  3. Save.
  4. Deployments → menu ⋯ do build → Retry build.
Se o build passar do token e falhar nas migrações: o Deploy command é npm run deploy, que roda as migrações antes de publicar — e o token automático do Workers Builds não inclui D1. Nesse caso: acrescente D1: Edit ao token, ou troque o Deploy command para npx wrangler deploy e deixe as migrações para o atualizar_motor_nuvem.cmd (que já faz isso e sempre funcionou).
Não quer brigar com token agora? Não precisa: em 21/09 o atualizar_motor_nuvem.cmd publicou o worker 5.26.4 com sucesso (conferido em /health). O automático é conveniência; o manual é o caminho garantido.

Parte 2 — Site de teste (Pages) na branch nova

  1. Na mesma tela Workers & Pages, clique no projeto teste-60f.
  2. Abra Settings → Builds & deployments → Production branch.
  3. Troque para arena/01a0cf4a-teste → Save.
  4. Confira que a configuração de build segue: Framework = Nenhum, Build command = vazio, Output directory = / (o repositório é estático puro — não tem passo de build).
  5. Vá em Deployments → Retry deployment (ou aguarde o push desta branch disparar um novo).
  6. Conferir: abra https://teste-60f.pages.dev, dê Ctrl+F5 e olhe o rodapé: tem que mostrar v7.0.10.
Alternativa sem mexer no painel: o alias de preview da branch costuma responder em https://arena-01a0cf4a-teste.teste-60f.pages.dev — mas aí você volta a ter dois links diferentes. A troca da Production branch mantém um link só, que é a regra do projeto.
